# valve-src — справжній алгоритм VRS, з коду Valve

Це не наша реконструкція. Це файли з
[ValveSoftware/counter-strike_regional_standings](https://github.com/ValveSoftware/counter-strike_regional_standings),
теки `model/`, зняті 2 листопада 2026 (останній push у репозиторій — 5 жовтня).

Тут лежить відповідь на все, що я цілий день підганяв по виміряних точках.
Зберігаю не ввесь клон (він пів гігабайта через дампи матчів), а п'ять файлів,
у яких уся арифметика.

## Головне, і воно інше, ніж я думав

**Очки — не сума компонентів.** HLTV показує «400 + LAN wins + Opp. network +
Bounty offered + Bounty collected + H2H», і я два дні вважав це формулою. У коді
(`ranking.js`) усе влаштовано так:

```js
seedValue = середнє чотирьох модифікаторів
            { bountyCollected: 1, bountyOffered: 1,
              opponentNetwork: 1, lanFactor: 1, ownNetwork: 0 }

rankValue = remapClamped( seedValue, min(усі команди), max(усі команди),
                          400, 2000 )
```

Тобто сид — це **середнє**, а потім **лінійне розтягування по ВСІЙ таблиці**
в діапазон 400…2000. Звідси два наслідки, яких із HLTV-вигляду не видно:

- очки команди залежать від **min і max усієї таблиці**, тож коли хтось угорі
  чи внизу рухається, перерахунок зачіпає всіх;
- «400» — це не вільний член, а нижня межа remap.

**Криві інші.**

```js
curveFunction( x ) = 1 / ( 1 + |log10(x)| )     // bountyCollected, bountyOffered
powerFunction( x ) = x                          // opponentNetwork, lanFactor
bucketSize = 10                                 // «десять найкращих» — вгадано правильно
referenceWinnings = 5-та найбільша сума призових серед усіх команд
bountyOffered = min( scaledWinnings / referenceWinnings, 1 )
```

Мій `19,4·(Σ)^0,23` був підгонкою під цю криву на вузькому діапазоні. І
призові рахуються **відносно п'ятої найбагатшої команди**, а не в доларах.

**H2H — це Glicko з фіксованим RD=75, тобто Elo** (`glicko.setFixedRD(75)`):

```js
Q  = Math.log(10) / 400
g  = 1 / Math.sqrt( 1 + 3*Q*Q*rd*rd / (π*π) )
ev = 1 / ( 1 + Math.pow( 10, g*(r-ro) / -400 ) )

adjRDSq = 1 / ( 1/(rd*rd) + Q*Q * g*g*ev*(1-ev)*info*info )
rank   += Q * adjRDSq * g * (score - ev) * info
```

- **RD=75 я вгадав точно.**
- **D=817,4 — ні.** Справжній знаменник 400, а масштаб дає множник `g`.
- `informationContent` — той самий «вага матчу», навколо якого я цілий день
  ходив: спершу помилково вчепив `weight(ev)`, потім зняв. Він є, але це
  окремий вхід від завантажувача даних, не вага призового фонду.
- Матчі проходяться **по черзі**, кожен застосовується одразу
  (`singleMatch`), а не пачкою на подію.

**Відсів.** У таблицю не потрапляє команда з `distinctTeamsDefeated === 0`, а
`satisfiesRankingCriteria` вимагає `matchesPlayed >= 5`.

## Що з цього робити наступного разу

Не підганяти. Узяти `model/` з клоном даних і **порахувати**. Тоді зникають
усі місця, де ми сьогодні впиралися в пів очка: і порядок fnatic проти HOTU,
і стеля 100 Thieves, і компенсація H2H за підняту базу.

У репозиторії ще є `invitation/` і `live/` — офіційні зрізи Valve по місяцях,
останній `2026_10_05`. Це еталон, на якому можна перевіряти власний прогін.

Повний клон у `.gitignore` (`openvrs/`) — покласти туди, і три старі скрипти
(`calib-step`, `epl-into-vrs`, `swing`) знову працюватимуть.
